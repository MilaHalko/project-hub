# Invites Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** The project owner invites a user by login (`POST /project/<id>/invite?user=<login>`). The owner removes a participant, or a participant leaves (`DELETE /project/<id>/members/<user_id>`).

**Architecture:**
- Two service functions in `projects/service.py` start with `get_project`, as every project function does.
- Both use `uow.projects` repository methods on both backends (ORM and SQL).
- Results go to the security log through the existing `_log_event`.
- No migration: `project_members` from `0003` is enough.

**Tech Stack:** FastAPI, pydantic 2, SQLAlchemy 2 async, psycopg 3, pytest, Poetry, ruff, pyright strict.

**Spec:** `docs/superpowers/specs/2026-11-15-invites-design.md` (read it; the acceptance criteria numbers below refer to it).

## Global Constraints

- **Paths and parameters exactly as written.** Invite: `POST /project/{project_id}/invite` with the query parameter `user`, no body. Removal: `DELETE /project/{project_id}/members/{user_id}`.
- **Error texts, verbatim:**
  - `Project not found`
  - `Only the project owner can invite users`
  - `User not found`
  - `You already own this project`
  - `User is already a participant of this project` (already raised by the repository)
  - `Only the project owner can remove participants`
  - `The owner cannot leave the project`
  - `Participant not found`
- **Check order.** It is the design's tables, and the first failing check decides the answer.
- **Repositories.** Every repository change goes into the `ProjectRepository` Protocol, `OrmProjectRepository` and `SqlProjectRepository`. Each one gets a contract test in `tests/projects/test_repository_contract.py`; the `database` fixture runs it for both backends.
- **API tests.** They use the `api_client` fixture (both backends), `signed_in`, `bearer`, `create_project` and `add_participant` from `tests/support/`.
- **Tests need Postgres.** Run `docker compose up -d --wait db`. If port 55433 is taken by another worktree's compose, export `TEST_DATABASE_URL=postgresql://project_hub:project_hub@localhost:55433/postgres` to reuse that server: tests create and drop their own database.
- **Comments.** None, and no docstrings, unless one explains a hidden reason that makes code unsafe to change. Never delete an existing comment.
- **Commits.**
  - One commit per task, with a subject in plain words.
  - Never add a `Co-Authored-By` trailer.
  - Before committing, check the diff for new `#` and `"""` lines.
- **Do not touch** `frontend/` or `docs/frontend/`.

## Review Focus

1. **A non-ASCII or multi-line `?user=` value** (`аня`, `anna\n`) → 404 `User not found`, never a 500. The log stays one line. → Task 1, `test_invite_odd_but_valid_login_is_user_not_found`.
2. **A user who has left** calls removal or invite again with a token that is still valid → 404 `Project not found`. → Task 2, `test_after_leaving_project_routes_are_404`.
3. **The owner removes the same participant twice** → the second answer is 404 `Participant not found`. → Task 2, `test_remove_twice_second_is_participant_not_found`.
4. **A removed participant's other routes** (`PUT …/info`, `GET …/members`) → 404 straight away, not only `GET …/info`. → Task 2, `test_after_leaving_project_routes_are_404`.
5. **Removal does not move the project** in `GET /projects`: `updated_at` is unchanged. → Task 2, `test_remove_keeps_updated_at`.
