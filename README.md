# Project Hub

Project Hub is a FastAPI service for managing projects. This repository holds the base
skeleton: an app factory, typed settings and a health endpoint. See
[`docs/initial-spec.md`](docs/initial-spec.md) for the product spec.

The web frontend lives in its own container; see [`frontend/README.md`](frontend/README.md).

## Requirements

- Python 3.13 and [Poetry](https://python-poetry.org/) 2.2+.
- If your default `python3` is older than 3.13, run `poetry env use python3.13` before `poetry install` (Poetry does not download Python for you).
- The virtualenv is created in `.venv/` (configured in `poetry.toml`).

## Setup

```bash
poetry install
cp .env.example .env
```

## Run

```bash
poetry run uvicorn project_hub.main:app --reload
```

Interactive API docs are served at <http://localhost:8000/docs>.

## Docker

```bash
docker compose up --build
```

This starts PostgreSQL 18 (`db`), the moto S3 emulator (`s3`), two one-shot services
(`migrate`, `storage-init`) and the API (`api`).
`migrate` waits for the database to be healthy, runs `python -m project_hub.db.migrate`
(`alembic upgrade head`) and exits; `storage-init` waits for `s3`, runs
`python -m project_hub.storage.create_bucket` (creates `APP_S3_BUCKET` if it is missing) and
exits. The API starts only after both completed successfully and is served at
<http://localhost:8000>.

| Service | Host port | Override with |
|---|---|---|
| `api` | 8000 | `APP_PORT` |
| `db` | 55433 | `APP_DB_PORT` |
| `s3` | 55435 | `APP_S3_PORT` |
| `mail` | 55436 (SMTP), 8025 (inbox) | `APP_MAIL_PORT`, `APP_MAIL_UI_PORT` |
| `storage-init` | — | one-shot, exits 0 |

The database uses 55433 so it does not clash with local Postgres servers on 5432 or 5433. Set the variables
in `.env` (see `.env.example`) or in the shell, for example `APP_PORT=8010 docker compose up`.
The `POSTGRES_*` values are local development credentials only; they take effect only when
the database volume is first created (run `docker compose down -v` to reset it).

The tests expect the `db`, `s3` and `mail` services to be running:

```bash
docker compose up -d --wait db s3 mail
```

Stop everything with `docker compose down` (add `-v` to delete the database volume).

## Database

The data layer has two interchangeable backends behind the same repository and Unit of Work
protocols, selected with environment variables (see `.env.example`):

| Variable | Values | Meaning |
|---|---|---|
| `APP_DB_BACKEND` | `orm` (default), `sql` | SQLAlchemy ORM or plain psycopg SQL |
| `APP_DATABASE_URL` | `postgresql://user:pass@host:port/db` | Database to use; when unset the app starts without a database |

Docker compose forwards `APP_DB_BACKEND` (default `orm`) to the `api` service, so setting it in
`.env` or the shell also selects the backend there.

Apply the migrations to the database in `APP_DATABASE_URL` (docker compose does this for you
in the `migrate` service):

```bash
poetry run alembic upgrade head
```

After `pip install` of the wheel, the `project-hub-migrate` command does the same; it reads `APP_DATABASE_URL`.

Migrations are written by hand, not autogenerated, so the schema stays independent of the ORM
models. To add one:

```bash
poetry run alembic revision -m "describe the change"
```

Then fill in `upgrade()` and `downgrade()` in the new file under
`src/project_hub/db/migrations/versions/`.

| Revision | Change |
|---|---|
| `0001` | creates `users` (`id`, `login` unique, `password_hash`, `created_at`) |
| `0002` | adds `users.token_version` (`integer NOT NULL DEFAULT 0`; existing rows get `0`) |
| `0003` | creates `projects` (`owner_id` → `users`, `RESTRICT`) and `project_members` (participants), indexes on `owner_id` and `user_id` |
| `0004` | creates `documents` (`project_id` → `projects`, `CASCADE`; `uploaded_by` → `users`, `SET NULL`; unique `storage_key`; checks on name length, content type and size), index on `project_id` |
| `0005` | creates `project_shares` (email share links: `project_id` → `projects`, `CASCADE`; unique `(project_id, email)` and `token_hash`; checks on email length and the hash format) |

## File storage

Files are stored in S3 through the small `FileStorage` interface (`storage/files.py`:
`put`, `get`, `delete`), implemented with boto3 in `storage/s3.py`. Locally and in CI the
S3 API is served by [moto](https://github.com/getmoto/moto) (`motoserver/moto`), so no AWS
account is needed. moto keeps files in memory: they are lost when the `s3` container stops,
while the database rows stay (run `docker compose down -v` to reset both).

| Variable | Default | Meaning |
|---|---|---|
| `APP_S3_BUCKET` | unset | Bucket for files; when unset the app starts without file storage and logs a warning |
| `APP_S3_ENDPOINT_URL` | unset | S3 endpoint; set for moto (compose uses `http://s3:5000`), unset for real AWS |
| `APP_S3_REGION` | `eu-west-1` | Bucket region |

Blank values count as unset. AWS credentials are not app settings: boto3 reads its standard
chain (`AWS_ACCESS_KEY_ID`/`AWS_SECRET_ACCESS_KEY` locally, the task role in AWS). Compose,
CI and the tests use the dummy keys `test`/`test`, which moto accepts. Never put real AWS
keys in `.env`, compose or CI. When the storage cannot be reached, or a bucket or file is
missing, the API answers `503 {"detail": "File storage is unavailable"}` and logs the cause.

## Storage usage Lambda

`project_hub.storage_usage.handler.handler` is a standalone AWS Lambda (it imports only the
standard library, `boto3` and `psycopg`). S3 sends `Object Created` and `Object Deleted`
events through EventBridge to an SQS queue, which triggers it in batches. For each project
named in the batch it lists `projects/<project_id>/documents/` in the bucket, sums the object
sizes and writes `projects.storage_used_bytes`, unless a newer figure (`storage_counted_at`)
is already stored. Messages of a project that could not be counted are returned in
`batchItemFailures` and retried; unknown projects and unrelated keys are ignored.
Each project counted in a run logs one JSON line, `"message": "storage usage counted"` with
`project_id` and `bytes`; when no row was written (the project is gone or a newer figure is
stored) the line says `"storage usage not stored"` and adds a `reason`.

| Variable | Default | Meaning |
|---|---|---|
| `APP_DATABASE_URL` | unset | PostgreSQL URL (a `+driver` part such as `postgresql+psycopg://` is accepted) |
| `APP_DATABASE_URL_PARAMETER` | unset | SSM parameter holding the URL, read with decryption once per cold start; used when `APP_DATABASE_URL` is unset |
| `APP_S3_ENDPOINT_URL` | unset | S3 endpoint; set for moto, unset for real AWS |
| `APP_S3_REGION` | `eu-west-1` | Bucket region |

## Image preview Lambda

`project_hub.image_preview.handler.handler` is a standalone AWS Lambda (it imports only the
standard library, `boto3` and Pillow, and never touches the database). S3 sends `Object Created`
and `Object Deleted` events for `projects/<project_id>/documents/<name>` through EventBridge
straight to it. For a created object it reads the bytes, and when they are a JPEG or PNG (by
signature) it writes a JPEG preview to `projects/<project_id>/previews/<name>.jpg`: at most
512 x 512 px, aspect ratio kept, never enlarged, EXIF orientation applied, transparency flattened
onto white, quality 80, `Content-Type: image/jpeg`. For a deleted object it deletes that preview.
Other keys are ignored. Files that are not images, cannot be read, exceed Pillow's
`MAX_IMAGE_PIXELS` guard or no longer exist get no preview and are not retried (the line
`image preview skipped` carries the key and the reason). S3 errors are raised, so Lambda's
asynchronous invoke retries the event up to 2 times within an hour (up to 3 invocations) and
then sends it to the function's dead-letter queue; EventBridge's own retries cover only a
failed delivery to the function. The other lines are `image preview stored` and
`image preview deleted`. Pillow is a dev dependency only: the API never imports it.

| Variable | Default | Meaning |
|---|---|---|
| `APP_S3_ENDPOINT_URL` | unset | S3 endpoint; set for moto, unset for real AWS |
| `APP_S3_REGION` | `eu-west-1` | Bucket region |

## Mail

The app sends plain-text mail over SMTP through the small `Mailer` interface
(`mail/mailer.py`: `OutgoingMail`, `SmtpMailer`, `MailDeliveryError`). Locally and in CI the
mail is caught by [Mailpit](https://mailpit.axllent.org) (`axllent/mailpit`), so nothing is
really sent: start it with `docker compose up -d --wait mail` and read the mail in the inbox at
`http://localhost:8025`. Compose points the `api` at it (`mail:1025`).

| Variable | Default | Meaning |
|---|---|---|
| `APP_SMTP_HOST` | unset | SMTP server; when unset the app starts without mail |
| `APP_SMTP_PORT` | `25` | SMTP port (1-65535) |
| `APP_MAIL_FROM` | `noreply@project-hub.test` | Sender address |
| `APP_PUBLIC_URL` | unset | Public base URL of the API (`http`/`https`, no query, trailing `/` dropped), used for the link in share mail; when unset sharing answers `503`. Compose sets `http://localhost:${APP_PORT}` |
| `APP_WEB_URL` | unset | Base URL of the web app (same rules as `APP_PUBLIC_URL`); when set, `GET /join` sends a browser without a sign-in there (see "Share by email"). Compose passes it on, empty by default |

A blank `APP_SMTP_HOST`, `APP_PUBLIC_URL` or `APP_WEB_URL` counts as unset. When the server
cannot be reached or refuses the mail, sending raises `MailDeliveryError`.

## Auth

`POST /auth` registers a user. The JSON body takes `login`, `password` and `repeat_password`;
on success it answers `201` with `id`, `login` and `created_at` (never the password or its hash).

- `login`: 3-32 characters from `A-Z a-z 0-9 _ . -`, case-sensitive, never trimmed. A taken
  login gives `409`.
- `password`: 8-128 characters of printable ASCII only (English letters, digits, keyboard
  symbols and spaces; Cyrillic, accents, emoji, tabs and newlines give `422`), stored exactly
  as typed, and it must not equal the login. `repeat_password` must match it. The rule applies
  to new passwords only: the `password` of `/login` and `current_password` accept any characters,
  so a wrong one is a `401` or `400`, never a `422`.
- Invalid input gives `422`. The error list never echoes the submitted values, so a rejected
  password does not end up in a response or a log.

Passwords are stored as Argon2id hashes (`argon2-cffi` defaults); the random salt and the
parameters live inside the hash string, so there is no separate salt column. Hashing runs in a
worker thread so it does not block the event loop.

`POST /login` takes `login` and `password` and answers `200` with
`{"access_token", "token_type": "bearer", "expires_in": 3600}`. The token is a JWT (HS256) valid
for exactly one hour. An unknown login and a wrong password give the same `401`
(`Invalid login or password`) and take about the same time (the password is verified against a
dummy hash when the login does not exist).

`APP_JWT_SECRET` signs the tokens: at least 32 characters, never committed. Generate one with
`python -c "import secrets; print(secrets.token_urlsafe(32))"`. An empty or whitespace-only
value counts as not set; without it the app starts and `/health` works, but `POST /login` answers
`500` (logged). A too-short value stops the start with an error that does not print the value, and
database errors are logged without bound parameters (no password hashes in logs).

`GET /users/me` returns the current user (`id`, `login`, `created_at`). Send the token as
`Authorization: Bearer <access_token>`. The token is checked for signature (HS256 only), expiry and
the required claims (`sub`, `ver`, `iat`, `exp`); the user must still exist and its `ver` must match
the user's current `token_version`. Anything else, including a missing header, gives `401` with
`WWW-Authenticate: Bearer`. In Swagger (`/docs`) click "Authorize" and paste the `access_token`
from `POST /login`.

`POST /logout` (with the token) answers `204` with no body and ends every session of the user, on
every device. Each user has a `token_version` number that every token carries as its `ver` claim;
logout adds one to it, so all tokens issued before (with the old `ver`) get `401` from then on,
and the next `POST /login` gives a working token again.

`PUT /users/me/password` (with the token) takes `current_password`, `new_password` and
`repeat_new_password` and answers `200` with a fresh token, like `/login`. The new hash and
`token_version + 1` are stored in one statement, so every other session ends (old tokens get `401`).
A wrong `current_password` gives `400`. `new_password` follows the same rules as at registration
(8-128 printable ASCII characters, must match the repeat, must differ from the current one and
from the login) and breaking them gives `422`. There are two `422` shapes: pydantic body errors
are a list (`{"detail": [{"loc", "msg", "type"}]}`), while the login rule is checked in the
service and gives `{"detail": "Password must not equal the login"}`. Neither echoes the
submitted passwords.

Security events are logged at INFO by `project_hub.auth.service` (`user registered`, `login
succeeded`, `login failed`, `logout`, `password changed`) with the login and user id; passwords,
hashes and tokens never appear in the log. An unknown login in `login failed` is masked to its
first two characters (`my***`), since it may be a password typed into the login field. The app
writes `project_hub.*` records at INFO and above to stderr (also under `uvicorn`); a missing
`APP_JWT_SECRET` logs one startup warning (`APP_JWT_SECRET is not set; login is disabled`). The
`uvicorn` access log shows a join link's `?token=` value as `token=***`.

Later routes that need a logged-in user take the `CurrentUser` dependency
(`from project_hub.auth.dependencies import CurrentUser`) as a parameter.

### Known limitations and future improvements

- Brute-force protection on `/login` (important): no rate limit or lockout yet; the plan is to
  count failed attempts per login and per IP and answer `429` after a threshold.
- `DELETE /users/me` is not implemented; it comes after epic 6, because deleting a user must also
  delete their projects and their S3 files. Until then `projects.owner_id` is `RESTRICT`, so a
  user who owns projects cannot be deleted. The planned endpoint answers a clear `409` such as
  `{"detail": "Delete your projects first"}`, never a bare `500`, and the frontend explains why
  and links to "My projects" (`GET /projects?role=owner`). When it lands, a user deleted in the middle
  of an invite must answer `404` `User not found` (today the `fk_project_members_user_id_users`
  violation would be a `500`; unreachable now because users cannot be deleted).
- Projects: no search by name (`GET /projects?q=`); no total count for paging (ask for `limit + 1`
  items); no index on `updated_at`; no transfer of ownership.
- The security log has no client IP address yet; it comes with epic 8 (behind the load balancer
  it is read from `X-Forwarded-For`).

## Projects

Every project route needs `Authorization: Bearer <access_token>` (`401` with
`WWW-Authenticate: Bearer` otherwise).

`POST /projects` takes `name` and `description` and answers `201` with the project; the caller
becomes its owner:

```json
{
  "id": "…",
  "name": "Diploma",
  "description": "Final project",
  "owner": {"id": "…", "login": "mila"},
  "my_role": "owner",
  "created_at": "2026-11-14T10:00:00Z",
  "updated_at": "2026-11-14T10:00:00Z",
  "storage_used_bytes": 0,
  "storage_limit_bytes": 52428800
}
```

- `storage_used_bytes` is the total size of the project's documents; `storage_limit_bytes` is
  `APP_PROJECT_MAX_BYTES` (default 52428800 = 50 MB, 1-10737418240). Every project response
  carries both.
- `name`: leading and trailing whitespace is stripped, then 1-100 characters, with no control
  character anywhere (Unicode category `Cc`: no newline, tab, NUL or U+007F); it is a one-line
  title. Duplicate names are allowed, also for one owner.
- `description`: 0-2000 characters, default `""`, kept exactly as sent (newlines and tabs are
  fine); only NUL is rejected, because Postgres `text` cannot store it.
- Breaking a rule gives `422`, never `500`, and nothing is stored.

`GET /project/{project_id}/info` returns the same project for its owner. For anyone without
access the answer is `404` `{"detail": "Project not found"}`, exactly as for an id that does not
exist, so an outsider cannot tell that the project exists. An id that is not a UUID gives `422`.
Participants (added by invites in epic 5) read and edit like the owner.

`PUT /project/{project_id}/info` replaces both `name` and `description` with the same rules as
creation and answers `200` with the updated project. The owner and participants may use it; the
owner and `my_role` do not change. An omitted `description` becomes `""`, so send the current one
to keep it. It sets `updated_at`, which moves the project to the top of `GET /projects`.
Outsiders and unknown ids get the same `404` as for reading; a bad body gives `422` and changes
nothing.

`GET /projects` lists every project the caller owns or participates in, each in the same shape
plus `"documents"`: that project's documents (same shape as `GET /project/{id}/documents`, newest
first, `[]` when it has none), read for the whole page in one query. The list is ordered by
`updated_at` newest first, ties broken by `id`, so pages never overlap or skip.
Query parameters:

- `limit`: 1-100, default 50; `offset`: 0-100000, default 0.
- `role`: `owner` (only my projects) or `participant` (only projects shared with me); absent
  means both.
- Any other value gives `422`.

The response is a plain list with no total count: to know whether there is a next page, ask for
`limit + 1` items.

`DELETE /project/{project_id}` deletes the project and answers `204` with no body. Only the owner
may do it: a participant gets `403` `{"detail": "Only the project owner can delete the project"}`;
an outsider or an unknown id gets the same `404` as for reading. The participants' access goes
with the project (their `project_members` rows are removed). The project's documents are
deleted with it, and so are their files in S3; if S3 is unavailable the answer is still `204` and a
WARNING `document files left in storage` lists the keys to remove by hand.

`GET /project/{project_id}/members` lists who has access: the owner first (`"role": "owner"`,
`joined_at` equal to the project's `created_at`), then the participants in the order they joined
(ties by login). Each item is `{"id", "login", "role", "joined_at"}`. The access rule is the same as
for reading the project: the owner and participants get `200`, an outsider or an unknown id gets
the `404` above. There is no paging, because a project has a handful of members. `avatar` comes
with the frontend epic F1.

`POST /project/{project_id}/invite?user=<login>` makes the user with that exact login (no case
folding, no trimming) a participant at once, with no acceptance step. Only the owner may do it. The
checks run in this order:

- `422` `{"detail": [...]}` if `user` is missing, empty, longer than 32 characters or contains
  NUL, or if `project_id` is not a UUID; the project and the invited login are not looked up;
- `404` `{"detail": "Project not found"}` for an outsider or an unknown id;
- `403` `{"detail": "Only the project owner can invite users"}` for a participant;
- `404` `{"detail": "User not found"}` if no user has that login;
- `409` `{"detail": "You already own this project"}` if the login is the owner's;
- `409` `{"detail": "User is already a participant of this project"}` if the user is already in.

On success it answers `201` with the new member, `{"id", "login", "role": "participant",
"joined_at"}`, the same item that `GET /project/{project_id}/members` then shows. The project's
`updated_at` does not change.

`DELETE /project/{project_id}/members/{user_id}` removes a participant and answers `204` with no
body. The owner removes any participant; a participant may remove only themself, which is how they
leave. The checks run in this order:

- `422` `{"detail": [...]}` if `project_id` or `user_id` is not a UUID;
- `404` `{"detail": "Project not found"}` for an outsider or an unknown id;
- `403` `{"detail": "Only the project owner can remove participants"}` for a participant who names
  someone else;
- `409` `{"detail": "The owner cannot leave the project"}` if the owner names themself;
- `404` `{"detail": "Participant not found"}` if `user_id` is not a participant of the project.

Whoever was removed or left gets the normal `404` for the project afterwards, and it disappears from
their `GET /projects`. They can be invited again and get a new `joined_at`. The project's
`updated_at` does not change.

Creating and deleting a project, inviting a participant and removing one are logged at INFO by
`project_hub.projects.service` as `project created`, `project deleted`, `participant invited`,
`participant removed` (the owner removes someone) and `participant left` (a participant removes
themself), with the login, user id and project id (and `member_id`, the invited, removed or leaving
user, for the participant events); the project name is not logged. Refused requests (`403`, `404`,
`409` and `422`) are not logged.

## Documents

A project keeps its documents (pdf, docx, jpg and png). The files live in S3 (see `## File storage`);
Postgres keeps what is known about them. Every document route needs
`Authorization: Bearer <access_token>` (`401` with `WWW-Authenticate: Bearer` otherwise). The
owner and the participants of the project have the same rights; anybody else gets
`404 {"detail": "Project not found"}`, exactly as for a project id that does not exist.

`POST /project/{project_id}/documents` uploads one or several files as `multipart/form-data`
in the field `files` (Swagger shows a file picker) and answers `201` with the new documents in
the order sent:

```json
[
  {
    "id": "…",
    "project_id": "…",
    "name": "thesis.docx",
    "content_type": "application/vnd.openxmlformats-officedocument.wordprocessingml.document",
    "size": 482113,
    "uploaded_by": {"id": "…", "login": "anna"},
    "created_at": "2026-11-15T10:00:00Z",
    "updated_at": "2026-11-15T10:00:00Z"
  }
]
```

The token and the access to the project are checked before the request body is read, so a
caller without access never makes the server parse the files. Then the files are checked, all
of them before anything is stored:

- Count: no `files` part → `422 No files were sent`; more than `APP_DOCUMENT_MAX_FILES`
  (default 10, 1-100) → `422 Too many files: at most 10 per request`. A body that is not valid
  multipart → `422 Invalid multipart form: …`.
- Name: only the part after the last `/` or `\` is kept, then surrounding whitespace is
  stripped (`../../etc/x.pdf` becomes `x.pdf`). Missing → `422 File name is missing`; longer
  than 255 characters or with a control character → `422`. The name is stored as cleaned (path
  part dropped, whitespace stripped) and never decides where the file goes in S3.
- Extension: `.pdf`, `.docx`, `.jpg`, `.jpeg` or `.png`, in any case → else `422 <name>: only pdf,
  docx, jpg and png documents are allowed`.
- Size: at most `APP_DOCUMENT_MAX_BYTES` (default 10485760 = 10 MB, 1-104857600) → else
  `413 <name>: file is larger than 10 MB`; an empty file → `422 <name>: file is empty`.
- Content: a pdf starts with `%PDF-`; a docx is a zip that lists `[Content_Types].xml` and
  `word/document.xml` (only the list of members is read, nothing is unpacked). It must match the
  extension → else `422 <name>: content is not a valid pdf` (or `docx`, `jpeg`, `png`). A jpeg
  starts with `FF D8 FF`, a png with the 8-byte PNG signature (only the start is read). The
  stored `content_type` is `application/pdf`,
  `application/vnd.openxmlformats-officedocument.wordprocessingml.document`, `image/jpeg` or
  `image/png`, whatever the client sent.
  Migration `0007` allows the two image types; its downgrade fails while any jpg or png document
  exists (delete those documents first).

A request is all or nothing: one bad file and none of its files is stored. Each file goes to
S3 under a new key `projects/<project_id>/documents/<random>`, then the rows are written and
the project's `updated_at` is set, which moves it to the top of `GET /projects`. When the
storage cannot be reached the answer is `503 {"detail": "File storage is unavailable"}` and no
row is written; when writing the rows fails, the files already stored are deleted again. Two
documents with the same name in a project are allowed.

A project may hold at most `APP_PROJECT_MAX_BYTES` of documents (`storage_limit_bytes`). An upload
or replacement that would take the total above it answers
`413 {"detail": "Project storage limit reached: <used> of <limit> used, this upload needs <size>"}`
and stores nothing; reaching the limit exactly is fine.
The project row is locked while the check runs, so two parallel uploads cannot both slip in. A
replacement that does not make the file bigger, and a delete, are always allowed.

`GET /project/{project_id}/documents` answers `200` with the project's documents, newest first
(`created_at`, ties broken by `id`), in the same shape as above; a project without documents
gives `[]`.

`GET /document/{document_id}` answers `200` with the file bytes and the stored `Content-Type`.
The headers are `Content-Disposition: attachment; filename="<ascii name>"; filename*=UTF-8''<percent-encoded name>`
(quotes, backslashes, semicolons, control and non-ASCII characters become `_` in the plain
`filename`, the exact name is in `filename*`), `X-Content-Type-Options: nosniff` and
`Cache-Control: private, no-store`. A document of a project the user cannot see and an unknown id
both give `404 {"detail": "Document not found"}`; a file missing from storage gives `503`.
The route needs the Bearer header, so the frontend downloads with `fetch` and the Bearer header
and saves the response as a blob, not with a plain link.

`PUT /document/{document_id}` replaces the file of one document with exactly one new file in
the multipart field `file` (zero or several files → `422 Exactly one file is required`). The
id and `created_at` stay; `name`, `size`, `content_type`, `uploaded_by` (the caller) and
`updated_at` change, and a document may change type (a pdf may become a docx or a png, and so on). The new file is
checked like an upload, stored under a new key, and only then is the row switched and the old
file deleted; an invalid file, an unavailable storage (`503`) or a database failure leaves the
document and its old file as they were. The project's `updated_at` is set. The access rules
are those of the download (`404 Document not found` for an outsider or an unknown id).

Before anything else (even before the token check), `POST /project/{id}/documents` and
`PUT /document/{id}` pass a size guard that never reads the body: no `Content-Length` header →
`411 {"detail": "Content-Length is required"}`; a non-integer or negative one → `400 Invalid
Content-Length`; more than `APP_DOCUMENT_MAX_FILES × APP_DOCUMENT_MAX_BYTES + 1 MiB` for `POST`
(`APP_DOCUMENT_MAX_BYTES + 1 MiB` for `PUT`) → `413 {"detail": "Request is too large"}`. The
per-file `413` above stays and gives the precise message. Demo note: when the server answers the
early `413` while a browser is still sending a big body, the browser may show a connection reset
instead of the answer; demo the per-file `413` (a file just above the per-file limit) instead.

All files of one request are held in memory, so the maximum settings (100 files × 100 MiB) need
that much memory per request; the defaults (10 × 10 MB) are fine.

`DELETE /document/{document_id}` deletes the row, sets the project's `updated_at` and answers
`204` with no body; the access rules are those of the download. The file is removed from storage
after the commit; if that fails the answer is still `204` and a WARNING `document files left in
storage` with the key is logged by `project_hub.storage.files`.

Every uploaded, replaced or deleted document is logged at INFO by `project_hub.documents.service`
as `document uploaded`, `document replaced` or `document deleted` with the login, user id, project id and document id;
the file name is not logged.

## Share by email

`GET /project/{project_id}/share?with=<email>` mails a join link for the project to an address
and answers `200` with `{"email": "<address in lower case>", "expires_at": "<UTC time>"}`. The
link is `<APP_PUBLIC_URL>/join?token=<token>`: it works once and lasts 7 days. Only the SHA-256
hash of the token is stored (table `project_shares`); the token is never in the answer, the
database or the log. The checks, in order (the first that fails decides):

- no valid JWT → `401` (with `WWW-Authenticate: Bearer`), whatever the parameters;
- `APP_SMTP_HOST` or `APP_PUBLIC_URL` unset → `503 {"detail": "Email sharing is not configured"}`,
  also checked before the parameters;
- `project_id` not a UUID, `with` missing or not a valid address (at most 254 characters, no
  surrounding spaces) → `422`;
- an outsider or an unknown project → `404 {"detail": "Project not found"}`;
- a participant → `403 {"detail": "Only the project owner can share the project"}`;
- the project already has 10 pending (unused, unexpired) links to other addresses →
  `429 {"detail": "Too many pending share links for this project"}`;
- the SMTP server cannot take the mail → `503 {"detail": "Email could not be sent"}`, nothing is
  stored, and a WARNING `share mail could not be sent` is logged with the failure type in
  `reason` (never the link).

The address is compared and stored in lower case. Sharing again with the same address replaces
the link: the old one stops working. Expired links are deleted on the next share of that project.
The project's `updated_at` does not change.

`GET /join?token=<token>` lets a signed-in user join with the mailed link. Every answer of this
route carries `Cache-Control: no-store`, errors included, so a shared computer keeps no copy. The
checks, in order:

- `token` missing, empty or longer than 128 characters → `422`;
- no `Authorization` header, `APP_WEB_URL` set and `Accept` contains `text/html` (a browser that
  opened the mailed link) → `303` to `<APP_WEB_URL>/join?token=<token>` (token percent-encoded);
  the link stays pending and the web page then calls `/join` with the Bearer header;
- no `Authorization` header otherwise, a broken or expired JWT, or a header that is not `Bearer` (such as
  `Basic …`) → `401` (with `WWW-Authenticate: Bearer`); the link stays pending;
- no pending link with this token (unknown, expired, already used, replaced by a newer share, or
  its project deleted) → `404 {"detail": "Invite link is invalid or expired"}`, the same answer in
  every case;
- the caller already has access (owner or participant) → `200` with `already_member: true`; the
  link is **not** used up and stays for the real recipient;
- otherwise the link is used up and the caller becomes a participant → `200` with
  `already_member: false`.

The answer is `{"login": "<caller>", "already_member": <bool>, "project": {…}}`, where `project`
is the same object as `GET /project/{project_id}/info` (with `my_role`). `login` shows who joined,
for a shared computer. The link has no recipient check: whoever uses it first while signed in
joins. Two people using it at once: only one joins, the other gets the `404`. The project's
`updated_at` does not change.

A successful share is logged at INFO by `project_hub.shares.service` as `project shared` with the
login, user id, project id and the recipient's address. A successful join is logged as
`project joined` with the new participant's login and user id, the project id and the address the
link was sent to. Refused shares and joins, and joins with `already_member: true`, are not logged.
The token and its hash are never logged.

Demo: `docker compose up -d --build`, then in Swagger (`http://localhost:8000/docs`):

1. Register and log in as `mila`, authorize with the token, create a project and call the share
   route with an address such as `anna@example.com`.
2. Open the Mailpit inbox at `http://localhost:8025` and copy the token from the link in the mail.
3. Register and log in as `anna`, authorize with her token, and call `GET /join` with the copied
   token: `200`, `already_member: false`. `GET /project/{project_id}/info` now works for her.
4. Call `GET /join` with the same token again (as `anna` or anyone else): `404`.

## Cloud

The API runs on AWS (ECS Fargate, RDS PostgreSQL behind an HTTPS load balancer), described in Terraform under `infra/`.
A cheap persistent layer stays up; the billed layer is brought up for a checkpoint and destroyed.
See [`infra/README.md`](infra/README.md) for the steps.

## Build the package

```bash
poetry build                          # dist/project_hub-<version>-py3-none-any.whl and .tar.gz
python3.13 -m venv /tmp/hub && /tmp/hub/bin/pip install dist/*.whl
poetry run pytest -m package          # builds, installs into a clean venv, checks GET /health
```

The wheel is installed with `pip` by the dependency ranges in its metadata, not by `poetry.lock`.
`pytest -m package` builds into a temporary folder, or uses the files in `PACKAGE_DIST_DIR` if
it is set. It installs the wheel into a fresh virtualenv and runs every command from another
folder with `python -I`, so nothing from `src/` or `.env` is used. The default `pytest` run skips
these tests.

The package tests need network access to PyPI (for `pip` and for building the sdist) and a Postgres
test server for the migration tests: `TEST_DATABASE_URL`, or `docker compose up -d --wait db`
(port 55433). A relative `PACKAGE_DIST_DIR` is resolved from the repository root.

## Build the storage usage Lambda

```bash
bash scripts/build_storage_usage_lambda.sh            # dist/storage-usage-lambda.zip
bash scripts/build_storage_usage_lambda.sh out.zip    # or another path
docker compose up -d --wait db s3
poetry run pytest -m lambda_package -v
```

The zip holds `project_hub/storage_usage/` and `psycopg` plus `psycopg-binary` (versions from
`poetry.lock`) as Linux arm64 wheels for Python 3.13. boto3 comes from the Lambda runtime. The
handler is `project_hub.storage_usage.handler.handler`.

`pytest -m lambda_package` builds the zip, mounts it read-only into the AWS Lambda base image
`public.ecr.aws/lambda/python:3.13` (arm64) and invokes the handler with an SQS event, against the
test Postgres and S3 emulator reached as `host.docker.internal`. It needs Docker and network access
to PyPI and `public.ecr.aws`. The default `pytest` run skips it. `host.docker.internal` reaches
the compose ports with Docker Desktop, and in CI the service containers through `host-gateway`;
on a Linux host the compose ports are bound to `127.0.0.1` only, so containers cannot reach them.

## Checks

```bash
poetry run ruff check
poetry run ruff format --check
poetry run pyright
docker compose up -d --wait db s3 mail   # tests need Postgres, the S3 emulator and Mailpit
poetry run pytest
```

The tests create a throwaway database (`project_hub_test_<random>`) on the compose `db`
service and drop it when the session ends. Set `TEST_DATABASE_URL` (an admin URL with an explicit host and port, such as
`postgresql://project_hub:project_hub@localhost:55433/postgres`) to use a different server.
pytest reads it only from the shell environment, not from `.env`, so use
`export TEST_DATABASE_URL=...`, and keep its port and credentials in step with `APP_DB_PORT`
and `POSTGRES_*` if you change them.

Storage tests and API tests use a throwaway bucket (`project-hub-test-<random>`) on the
compose `s3` service, emptied after each test and deleted when the session ends. Set
`TEST_S3_ENDPOINT_URL` (default `http://localhost:55435`, in step with `APP_S3_PORT`) to use a
different emulator; like `TEST_DATABASE_URL` it is read only from the shell. When the emulator
does not answer, the run fails with a hint instead of skipping. The tests replace any AWS
credentials in the environment with the dummy `test`/`test` keys.

## CI

GitHub Actions (`.github/workflows/ci.yml`) runs on every pull request and every push to `main`.

- Job `checks`: the commands from `## Checks` on Python 3.13 with Postgres and moto services, then a
  step that fails unless the contract tests passed with both database backends (`orm` and `sql`).
- Job `docker`: `poetry run pytest -m docker`, the image and compose smoke tests, in parallel.
- Job `package`: `poetry build`, uploads `dist/` as the artifact `project-hub-dist` (kept 14 days),
  then `pytest -m package` on exactly those uploaded files.
- Job `lambda`: on an arm64 runner, builds `dist/storage-usage-lambda.zip`, uploads it as the artifact
  `storage-usage-lambda` (kept 14 days), then `pytest -m lambda_package` runs it in the Lambda image.

Results are on the pull request's Checks tab and in the repository's Actions tab. There is no
deploy yet (epic 8).

## Layout

Each feature gets its own package under `src/project_hub/<feature>/` with, as needed:
`router.py` (HTTP layer), `schemas.py` (request/response models), `service.py` (business
logic, no HTTP knowledge), `repository.py` (data access), `models.py` (ORM models) and
`dependencies.py` (FastAPI dependencies).

- Shared code lives in `core/`.
- `db/` holds the data layer: `base.py` (SQLAlchemy base), `uow.py` (Unit of Work protocol),
  `database.py` (`Database` protocol and factory), `orm.py` and `sql.py` (the two backends),
  `urls.py` (converts the plain Postgres URL for SQLAlchemy),
  `dependencies.py` (`get_uow`), `migrate.py` (runs `upgrade head`) and `migrations/`.
  It lives outside `core/` because the Unit of Work imports feature repositories.
- `documents/` follows the feature layout and adds `validation.py` (file name, size and content
  checks) and `forms.py` (reads the multipart form after the access check).
- `storage/` holds file storage: `files.py` (`FileStorage` protocol, `StorageUnavailableError`),
  `s3.py` (boto3 implementation), `create_bucket.py` (creates the bucket for compose) and
  `dependencies.py` (`Storage`).
- `users/` follows the feature layout: `entities.py`, `repository.py` (protocol), `models.py`
  (ORM model), `repository_orm.py` and `repository_sql.py`.
- `auth/` holds registration, login and tokens: `passwords.py` (Argon2 hashing), `tokens.py`
  (JWT issue and decode), `schemas.py`, `service.py`, `router.py` and `dependencies.py`
  (`CurrentUser`). `users/` also has `router.py` (`GET /users/me`), `service.py` and
  `schemas.py` for the user data other modules need.
- Feature modules depend on `core/`; `core/` never imports from feature modules.
- A module that needs another module calls that module's `service`, never its repository.
- Tests mirror this layout under `tests/<feature>/`.
- `infra/` holds the Terraform for AWS: `persistent/` (always on) and `ephemeral/` (database, load balancer, service), with a runbook in `infra/README.md`.
