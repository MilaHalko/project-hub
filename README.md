# Project Hub

Project Hub is a FastAPI service for managing projects. This repository holds the base
skeleton: an app factory, typed settings and a health endpoint. See
[`docs/initial-spec.md`](docs/initial-spec.md) for the product spec.

## Requirements

- Python 3.13 and [Poetry](https://python-poetry.org/) 2.2+.
- If your default `python3` is older than 3.13, run `poetry env use python3.13` before `poetry install` (Poetry does not download Python for you).
- The virtualenv is created in `.venv/` (configured in `poetry.toml`).

## Setup

```bash
poetry install
cp .env.example .env
```

## Run

```bash
poetry run uvicorn project_hub.main:app --reload
```

Interactive API docs are served at <http://localhost:8000/docs>.

## Docker

```bash
docker compose up --build
```

This starts PostgreSQL 18 (`db`), a one-shot `migrate` service and the API (`api`).
`migrate` waits for the database to be healthy, runs `python -m project_hub.db.migrate`
(`alembic upgrade head`) and exits; the API starts only after `migrate` completed
successfully and is served at <http://localhost:8000>.

| Service | Host port | Override with |
|---|---|---|
| `api` | 8000 | `APP_PORT` |
| `db` | 55433 | `APP_DB_PORT` |

The database uses 55433 so it does not clash with local Postgres servers on 5432 or 5433. Set the variables
in `.env` (see `.env.example`) or in the shell, for example `APP_PORT=8010 docker compose up`.
The `POSTGRES_*` values are local development credentials only; they take effect only when
the database volume is first created (run `docker compose down -v` to reset it).

Tests that need a database expect the `db` service to be running:

```bash
docker compose up -d --wait db
```

Stop everything with `docker compose down` (add `-v` to delete the database volume).

## Database

The data layer has two interchangeable backends behind the same repository and Unit of Work
protocols, selected with environment variables (see `.env.example`):

| Variable | Values | Meaning |
|---|---|---|
| `APP_DB_BACKEND` | `orm` (default), `sql` | SQLAlchemy ORM or plain psycopg SQL |
| `APP_DATABASE_URL` | `postgresql://user:pass@host:port/db` | Database to use; when unset the app starts without a database |

Docker compose forwards `APP_DB_BACKEND` (default `orm`) to the `api` service, so setting it in
`.env` or the shell also selects the backend there.

Apply the migrations to the database in `APP_DATABASE_URL` (docker compose does this for you
in the `migrate` service):

```bash
poetry run alembic upgrade head
```

Migrations are written by hand, not autogenerated, so the schema stays independent of the ORM
models. To add one:

```bash
poetry run alembic revision -m "describe the change"
```

Then fill in `upgrade()` and `downgrade()` in the new file under
`src/project_hub/db/migrations/versions/`.

## Auth

`POST /auth` registers a user. The JSON body takes `login`, `password` and `repeat_password`;
on success it answers `201` with `id`, `login` and `created_at` (never the password or its hash).

- `login`: 3-32 characters from `A-Z a-z 0-9 _ . -`, case-sensitive, never trimmed. A taken
  login gives `409`.
- `password`: 8-128 characters, stored exactly as typed, and it must not equal the login.
  `repeat_password` must match it.
- Invalid input gives `422`. The error list never echoes the submitted values, so a rejected
  password does not end up in a response or a log.

Passwords are stored as Argon2id hashes (`argon2-cffi` defaults); the random salt and the
parameters live inside the hash string, so there is no separate salt column. Hashing runs in a
worker thread so it does not block the event loop.

### Known limitations and future improvements

- Brute-force protection on `/login` (important): no rate limit or lockout yet; the plan is to
  count failed attempts per login and per IP and answer `429` after a threshold.
- `DELETE /users/me` is not implemented; it comes after epic 4.

## Checks

```bash
poetry run ruff check
poetry run ruff format --check
poetry run pyright
docker compose up -d --wait db   # tests need Postgres
poetry run pytest
```

The tests create a throwaway database (`project_hub_test_<random>`) on the compose `db`
service and drop it when the session ends. Set `TEST_DATABASE_URL` (an admin URL with an explicit host and port, such as
`postgresql://project_hub:project_hub@localhost:55433/postgres`) to use a different server.
pytest reads it only from the shell environment, not from `.env`, so use
`export TEST_DATABASE_URL=...`, and keep its port and credentials in step with `APP_DB_PORT`
and `POSTGRES_*` if you change them.

## CI

GitHub Actions (`.github/workflows/ci.yml`) runs on every pull request and every push to `main`.

- Job `checks`: the commands from `## Checks` on Python 3.13 with a Postgres service, then a
  step that fails unless the contract tests passed with both database backends (`orm` and `sql`).
- Job `docker`: `poetry run pytest -m docker`, the image and compose smoke tests, in parallel.

Results are on the pull request's Checks tab and in the repository's Actions tab. There is no
deploy yet (epic 8).

## Layout

Each feature gets its own package under `src/project_hub/<feature>/` with, as needed:
`router.py` (HTTP layer), `schemas.py` (request/response models), `service.py` (business
logic, no HTTP knowledge), `repository.py` (data access), `models.py` (ORM models) and
`dependencies.py` (FastAPI dependencies).

- Shared code lives in `core/`.
- `db/` holds the data layer: `base.py` (SQLAlchemy base), `uow.py` (Unit of Work protocol),
  `database.py` (`Database` protocol and factory), `orm.py` and `sql.py` (the two backends),
  `urls.py` (converts the plain Postgres URL for SQLAlchemy),
  `dependencies.py` (`get_uow`), `migrate.py` (runs `upgrade head`) and `migrations/`.
  It lives outside `core/` because the Unit of Work imports feature repositories.
- `users/` follows the feature layout: `entities.py`, `repository.py` (protocol), `models.py`
  (ORM model), `repository_orm.py` and `repository_sql.py`.
- `auth/` holds registration (and later login and tokens): `passwords.py` (Argon2 hashing),
  `schemas.py`, `service.py`, `router.py` and `dependencies.py`. `users/` also has `service.py`
  and `schemas.py` for the user data other modules need.
- Feature modules depend on `core/`; `core/` never imports from feature modules.
- A module that needs another module calls that module's `service`, never its repository.
- Tests mirror this layout under `tests/<feature>/`.
